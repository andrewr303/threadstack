## 3. Findings, most severe first

1. **Major | AC-10 / FR-4 / FR-8 | `bridge-query.ts:140`, `payload.ts:309-311`, `tools.ts:123-125` | FAIL on the real chain.**
   - Expected: a 200,000-character message gives a result of at most 60,000 characters, `truncated:true`, and the message ending `[…cut]`.
   - Actual: `messageOut` cuts at 120,000 with `[… cut: N more characters]`. `boundedResult` then cuts any string over 12,000 with `[… truncated]` and does not set `truncated`. The plugin reads `truncated` only from the extension, which sets it only for budget or window truncation. Result: the text ends `[… truncated]` and `truncated` is false.
   - The same 12,000-character cut silently drops the rest of any long message, with no flag and no way to page within it.
   - Fix: in `bridge-query.ts:134-152`, use the `[…cut]` marker and set `truncated = true` on a string cut. In `tools.ts:123` carry that flag through to the result.
   - Test: an extension test seeding a 200,000-character message, then asserting `ends with "[…cut]"` and `truncated === true`. Add a plugin test that uses real extension output.

2. **Major | AC-5 / FR-4 | `payload.ts:334-342`, `bridge-query.ts:145-149,214` | Newest messages are dropped and unreachable.**
   - Expected: newest 40 messages first, with `before` reaching all older ones.
   - Actual: when the page exceeds the 50,000-character budget, the window loop stops at the newest messages, and `boundedResult` pops the last array entries. The cursor is `transcript.from` (the window start). Dropped newest messages are never returned by any later call. The AC-5 test only uses tiny messages.
   - Fix (`bridge-query.ts` threads.get branch): keep the newest messages and drop the oldest within the budget, and set `before` to the first returned message's index. Do not use `largest.pop()` on `messages`.
   - Test: 300 messages of 3,000 characters each, paging with `before` until exhausted, asserting no gaps.

3. **Major | FR-7 / AC-9 | `server/src/__tests__/tool-gateway.test.ts` | Plugin handler not-run assertion absent.**
   - The deny policy is tested only at decision level (`tool-access-policy-service.test.ts:269-275`). There is no assertion that the plugin handler is not invoked.
   - Fix: add a tool-gateway test with a block policy and a handler spy.

4. **Major | AC-13 / FR-9 | `service.ts:124,44` | Offline error is not under 1 s in the first 40 s.**
   - Expected: browser closed gives `browser_offline` in under 1 s.
   - Actual: the immediate check fires only when `lastSeenAt` is older than `OFFLINE_MS` (40 s). Within 40 s of a close, the request queues until the heartbeat timer cancels it or the 30 s timeout fires. That is a wait of up to 30 s, and then a `timeout` error rather than `browser_offline`.
   - Fix options: use a shorter offline threshold, or have the extension signal a disconnect. Needs a live run to confirm.

5. **Minor | FR-9 | `service.ts:44,300` | Wrong error text on mid-request cancel.**
   - A request cancelled mid-flight uses `"The founder's browser is not connected."` without the "Continue without session data…" tail. `close()` uses `"The session bridge stopped."`.
   - Fix: use the exact FR-9 text in both. Test: cancel a pending request and compare the error.

6. **Minor | FR-2 / AC-8 | `contracts.ts:58` via `tools.ts:89`.**
   - Expected `bad_request: query is required`. Actual `bad_request: query is required and must contain at most 2000 characters`.
   - AC-8 only needs the `bad_request:` prefix, so this is an FR-2 scenario deviation. Fix: a dedicated message for empty input.

7. **Minor | AC-4 / FR-3 (REQ-13) | `background.ts:521-522`.**
   - When an extension workspace tab already exists, the code calls `chrome.tabs.update(tabId, {active:true})` but does not call `chrome.windows.update(windowId, {focused:true})`. If that tab is in another window, the window does not come forward. This is RUNTIME-ONLY to confirm. `openManagerTab` does focus a window (`background.ts:673`).
   - Fix: focus the tab's window after the successful open.

8. **Minor | AC-3 / FR-2 | `bridge-query.ts:169`.**
   - `degraded` is set only from configuration. With the default `allowRemoteModels=false` (`bridge.ts:66`), `best` always reports `local_only`.
   - A configured provider that fails at runtime is not reported as degraded. Fix: use the searchThreads outcome (the `semantic` and `reranked` flags). Test: `best` with a failing embed.

9. **Minor | FR-9 (REQ-13) | `worker.ts:77`.**
   - Each founder search keystroke pause writes a `browser_sessions.tool_called` activity entry with `agentId:"board"`. This is activity-log noise, not an agent read. Consider tagging those entries or skipping them for the board route.

10. **Minor | FR-5 | `bridge-query.ts:173-175`.**
    - `parseContext` clamps limit to 8, then the code overrides it to as much as 20. Confirm `threadContext` handles that. Add a test with `limit:20`.

11. **Minor | cursor length | `tools.ts:97` vs `protocol.ts:501,520`.**
    - The plugin accepts a cursor of up to 2000 characters. The extension rejects more than 200. This surfaces as a generic `bad_request`. Align the limits.

Checked and clean:
